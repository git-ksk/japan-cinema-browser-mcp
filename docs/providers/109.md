## 2026-08-13時点の公式公開導線

### 劇場一覧

```text
https://109cinemas.net/
```

トップページの「109シネマズの劇場」に、各劇場への公開linkが表示されています。

例:

```text
https://109cinemas.net/kohoku/
https://109cinemas.net/nagoya/
https://109cinemas.net/premiumshinjuku/
```

adapterは、画面に表示されたlinkから取得したslugだけを劇場IDとして採用します。劇場名からslugを生成・推測しません。

### 劇場ページと日付指定

通常館の例:

```text
https://109cinemas.net/kohoku/
```

上映スケジュールの日付controlには、公開済み日付だけ明示的なhrefがあります。

```text
https://109cinemas.net/kohoku/schedules/20260813.html?theater_code=13
```

プレミアム新宿ではquery形式が通常館と異なるため、`theater_code` 等の仕様を一般化しません。画面に表示されたhrefをそのまま採用し、遷移後も同じpath / queryであることを再確認します。

日付labelが表示されていてもhrefがない場合、その日付のrouteを推測生成しません。

### 上映ページから読む情報

公開schedule pageから次を確認します。

- 対象日付
- 作品名
- 上映開始・終了時刻
- シアター番号
- 2D / IMAX / 4DX / SCREENX / ULTRA 4DX等の上映方式
- 字幕 / 吹替、`SUB` / `DUB`
- 空席状態
- 購入導線の存在

adapterが構造化するのは、劇場・日付・作品・時間・screen・format・language・availabilityだけです。

availabilityは共通schemaへ次のように正規化します。

- `残席わずか` / `残りわずか` → `limited`
- `満席` / `完売` / `売り切れ` → `sold_out`
- `販売終了` / `販売開始前` → `unavailable`
- `空席あり`、または制約表示なし → `unknown`

`空席あり` から具体的な残席数は推測しません。

## 表示完了の判定

SPAや遅延描画を考慮し、固定sleepだけで結果を返しません。

短い上限付きpollingで、画面種別ごとに次を確認します。

- 劇場一覧: theater marker、境界、レビュー済み件数範囲の劇場link
- 劇場ページ: theater identity、schedule section、明示的な日付linkまたは空状態
- schedule page: 日付heading、上映rowまたは明示的な空状態

Chrome process / CDP targetは既存runtimeを再利用し、providerごとにbrowserを再起動しません。

## 安全停止する条件

次の場合は部分結果を推測せず停止します。

- 公式rootの劇場blockを識別できない
- 劇場数がレビュー済み範囲から大きく外れる
- theater linkがレビュー済みの `https://109cinemas.net/{slug}/` 形から外れる
- lookalike domain、credentials付きURL、non-default port
- 劇場queryを一意に解決できない
- 劇場pageのhostname / path / identityが要求劇場と一致しない
- 表示日付と明示schedule routeの日付が一致しない
- schedule hrefの劇場slugが要求劇場と異なる
- navigation後のpath / queryが表示hrefから変化した
- schedule headingの日付が要求日と異なる
- 上映回を作品またはscreenへ一意に結び付けられない
- 認識可能なrowが0件なのに明示的な空状態もない
- CAPTCHA / anti-bot challengeを検出した

未公開日付は、他の公開日付routeが正しく確認できる場合に限り `dateAvailable=false` として返します。hrefのない日付からrouteを作りません。

## 購入導線の扱い

劇場ページには `オンラインチケット購入`、上映回には購入導線が表示されます。

上映情報adapterはこれらを操作しません。

現在のcapabilityは:

```text
seatMap=true
seatSelection=false
checkoutPreparation=false
purchaseSubmission=false
```

です。

109対応のために汎用 `click_cinema_control`、sensitive-data guard、purchase gateを弱めることはありません。

## 利用規約・サイトポリシー

2026-08-13に109シネマズ公式サイトポリシー、株式会社東急レクリエーションのサイトポリシー、公式チケット購入方法を確認しました。

本プロジェクトはraw HTML / full DOM /画像等を保存・再配布せず、ユーザー要求時に必要な表示上の事実だけを一時的に扱います。

購入フローでは利用規約・注意事項への同意が必要ですが、読み取りadapterは購入フローへ入らず、同意controlも操作しません。

座席・checkout・purchase capabilityを変更する前、またはautomation surfaceを大きく変更する際には再レビューします。

## Phase 3 座席情報調査 — 2026-08-17

109シネマズ港北の現行scheduleから、公開UIに表示されたshowtime hrefをそのまま利用して座席表へ進みました。初期調査では座席自体をクリックしていません。

公式公開情報から確認できたこと:

- 上映回選択後、購入枚数分の座席を選び `次へ` 進む
- 詳細な座席表を確認できる公開UIがある
- seat holdは10分と明記されている
- 非会員は `入会せず購入に進む` を選べる
- 港北ではstandard / Executive / Pair / wheelchair seatを区別している

### 座席表へ入るだけではholdしない

追加検証で、10分timerは座席表へ入った直後から表示されることが分かりました。

一方、画面には `選択座席 0／8席` と表示され、同じ上映を独立した2つのbrowser sessionで開いて比較しても:

- 223 seats
- selected 0
- unavailable 11
- 座席ごとの状態差分 0

でした。

つまり座席表へのentryは10分の購入session文脈を作りますが、**entryだけでは座席holdや他sessionから見えるavailability変更を起こさない**という強い実測根拠があります。

#35で読み取り専用adapterを実装し、`seatMap=true` にしました。

adapterはschedule DOMに表示された正確な `cinema.109cinemas.net/.../resv_shw_ppt.cgi?...` hrefだけを採用し、date / startTimeへ再結合します。

座席ページでは `input.seat[type=checkbox]` のdisabled / checkedと `data-seat-key` を読み、10分timer表示と選択座席0件を必須確認します。

座席activationは引き続き変更操作として扱い、`seatSelection=false` です。

詳細: [`../PHASE3_SEAT_DISCOVERY.md`](../PHASE3_SEAT_DISCOVERY.md)

## Phase 4 現行UIの読み取り再確認 — 2026-08-17

現行座席ページでは、選択0件の表示が以前の形式から `選択座席：0／8席` のように全角colon付きへ変化していました。

以前のparserは旧表記だけを許可していたため、座席表を返す前に正しく安全停止しました。

現在は、同じレビュー済みlabelに限りASCII / 全角colonの有無を許容します。**選択座席0件であること自体の条件は緩めていません。**

修正後、独立したfresh temporary Chrome profile 2本で同じ上映を確認しました。

対象:

- 109シネマズ港北
- 2026-08-18
- `オークストリートの異変[字幕]`
- 11:15
- Screen 5

両profileで次が一致しました。

- レビュー済み10分解放案内
- `選択座席：0／8席`
- 94 seats
- available 83
- unavailable 11
- selected 0
- universal 2
- context / layout / stateのSHA-256 fingerprint

この確認では座席activation、`次へ`、会員・非会員継続、券種、同意、購入者情報、支払い、購入controlを操作していません。

これにより、座席表entryはtimed session contextを作るものの、entryだけでは座席holdやcross-session availability変更を起こさないことを再確認できました。

ただし座席変更を許可する根拠にはなりません。#52で正確なactivation / release境界を別途レビューするまで、`seatSelection=false` / `checkoutPreparation=false` / `purchaseSubmission=false` を維持します。
